> **Важно о названии.** Пользовательский бренд в верхней навигации уже называется **Tripalora**. В коде, базе данных, юридических текстах и названиях индексов пока сохраняется историческое имя **Fairworth**. Поэтому далее продукт называется Tripalora, а термины `Fairworth Score`, `fairworth_score` и технические ключи приводятся в их текущем виде. Перед публичным запуском потребуется отдельная полная миграция бренда.

## 2. Что представляет собой Tripalora

Tripalora — персонализированный сервис сравнения путешествий. Его задача — не просто показать пользователю список отелей и перелётов, а помочь понять, какой вариант лучше соответствует:

- бюджету;
- формату поездки;
- личным предпочтениям;
- требованиям к качеству;
- требованиям к удобствам;
- допустимому количеству пересадок;
- уровню надёжности доступных данных;
- актуальности и полноте цены.

Ключевая продуктовая идея состоит в разделении трёх понятий:

1. **Насколько вариант подходит пользователю.** Это показывает базовый персонализированный Score.
2. **Насколько достаточно данных для доверия этому Score.** Это показывает Score Reliability.
3. **Насколько можно доверять показанной цене.** Для отелей используется Price Confidence, для перелётов — Fare Confidence.

Такой подход не позволяет отсутствующим данным автоматически сделать хороший отель или перелёт плохим. Если провайдер не передал часть информации, соответствующий сигнал исключается из применимой формулы, а интерфейс сообщает, каких данных не хватило.

### 2.1. Что умеет текущий закрытый MVP

- регистрация, подтверждение почты, вход и восстановление пароля;
- заполнение персональных предпочтений;
- поиск отелей по поддерживаемым городам;
- загрузка и проверка реальных тарифов на выбранные даты и число гостей;
- строгая фильтрация по обязательным условиям;
- персональное ранжирование отелей;
- отображение уверенности в Score и цене;
- подробная страница отеля с галереей, тарифами и объяснением Score;
- AI-анализ отеля через OpenRouter;
- сравнение до трёх отелей;
- поиск и персональное ранжирование авиаперелётов;
- добавление отеля и перелётов в общую корзину поездки;
- демонстрационное оформление поездки без оплаты и реального бронирования;
- закладки, отслеживание цены и email-уведомления;
- сохранение поездок и напоминания;
- персональная карта посещённых стран и городов;
- управление сессиями, согласиями, экспортом и удалением данных;
- административный контроль импорта каталога, сопоставления отелей и аномалий.

### 2.2. Что текущий MVP намеренно не обещает

- Tripalora не принимает оплату;
- демо-бронь не создаёт реальную бронь у отеля или авиакомпании;
- партнёрские переходы и postback отключены флагом `PARTNER_BOOKING_ENABLED=false`;
- Travelpayouts Data API предоставляет индикативные, часто кешированные цены, а не подтверждённую доступность места;
- пакетный тур находится в Beta и не является полноценным продуктовым потоком;
- трансферы скрыты из основного MVP до подключения реального провайдера;
- абсолютное покрытие всех отелей мира одним developer API не заявляется.

## 3. Высокоуровневая архитектура

```text
Пользователь
    |
    v
React SPA / Vite
    |
    | HTTPS + JSON API + HttpOnly cookies + CSRF
    v
Node.js / Express API
    |
    +--> PostgreSQL
    |      - пользователи и предпочтения
    |      - каталог отелей и тарифы
    |      - поиски и взаимодействия
    |      - Score snapshots и аномалии
    |      - поездки, уведомления и достижения
    |
    +--> LiteAPI
    |      - каталог отелей
    |      - номера и live rates
    |
    +--> Xotelo
    |      - дополнительный источник цен отелей
    |
    +--> Google Places Photos
    |      - фотографии и галереи отелей
    |
    +--> Travelpayouts Data API
    |      - индикативные цены перелётов
    |      - аэропорты, города, страны, авиакомпании
    |
    +--> OpenRouter
    |      - персональный AI-анализ отеля
    |      - AI-вердикт сравнения
    |
    +--> SMTP
           - подтверждение почты
           - восстановление пароля
           - уведомления о ценах
           - напоминания и weekly digest

Notification Worker
    |
    +--> проверяет price watches
    +--> ставит уведомления в PostgreSQL queue
    +--> отправляет письма через SMTP
    +--> очищает данные по retention policy
```

### 3.1. Клиентская часть

Клиент построен на React 18, Vite и React Router. Основные экраны:

- главная страница и поисковая форма;
- регистрация, вход и auth actions;
- Preferences;
- результаты отелей;
- карточка отеля;
- сравнение отелей;
- поиск перелётов;
- корзина поездки;
- demo checkout;
- Insights;
- Achievements;
- юридические страницы;
- административный экран.

На клиенте также находятся:

- RU/EN локализация;
- глобальный контекст корзины поездки;
- Error Boundary;
- состояние доступности API-провайдеров;
- кеш последней выдачи в `sessionStorage`;
- защита маршрутов: авторизация, подтверждение email и завершённый onboarding.

### 3.2. Серверная часть

Express API выполняет:

- аутентификацию и авторизацию;
- валидацию входящих данных;
- изоляцию данных по `user_id`;
- работу с внешними провайдерами;
- нормализацию цен;
- расчёт индексов;
- запись аналитических событий;
- хранение и обновление пользовательского профиля;
- управление уведомлениями;
- формирование административной диагностики.

### 3.3. База данных

PostgreSQL является источником истины для:

- пользователей, согласий и сессий;
- предпочтений и обученных весов;
- контекстных профилей предпочтений;
- каталога отелей, номеров, удобств, фотографий и provider mappings;
- цен, проверок тарифов и ценовых наблюдений;
- отзывов, их свежести и согласованности источников;
- поисков, сравнений и взаимодействий;
- снимков Score и аномалий;
- достижений;
- демо-бронирований;
- задач уведомлений и истории их выполнения;
- административного аудита.

Схема развивается через 21 упорядоченную миграцию.

### 3.4. Фоновый worker

Отдельный процесс worker:

- регулярно проверяет активные отслеживания цен;
- чаще проверяет цены по мере приближения поездки;
- сохраняет каждое ценовое наблюдение;
- отправляет уведомление при падении примерно на 5% или достижении target price;
- отправляет уведомление при росте примерно на 7%;
- создаёт напоминания за 7 дней, 24 часа и 3 часа до поездки;
- формирует weekly digest;
- повторяет неуспешные email-задачи с увеличивающейся задержкой;
- восстанавливает зависшие задачи;
- применяет сроки хранения к пользовательским и техническим данным.

## 4. Внешние сервисы и их роли

| Сервис | Роль в Tripalora | Что происходит при недоступности |
|---|---|---|
| LiteAPI | Основной каталог отелей, номера и тарифы | Каталог или live rates не обновляются; UI показывает недоступность провайдера, синтетические цены не создаются |
| Xotelo | Дополнительный источник цен отелей | Поиск продолжает работать с доступными LiteAPI-тарифами |
| Google Places Photos | Несколько фотографий отеля | Используются 1-2 сохранённых изображения из каталога |
| Travelpayouts Data API | Индикативные цены перелётов и справочники | Flight capability становится недоступной, фиктивные билеты не подставляются |
| OpenRouter | AI-анализ отеля и AI-сравнение | Детерминированный Score продолжает работать; AI-функция сообщает о недоступности |
| SMTP | Системные письма и уведомления | В production задача повторяется и затем фиксируется как failed; в development используется Mailpit |
| SimpleMaps city data | Поиск городов для Achievements | Карта загружается, но справочник добавления городов временно недоступен |
| World Atlas | Геометрия интерактивной карты | Без локального ассета карта не сможет отрисовать страны |
| Sentry, опционально | Ошибки клиента и сервера | Основная логика продолжает работать, остаются structured logs |

### 4.1. Capability layer

`GET /api/capabilities` сообщает клиенту, какие функции действительно готовы. Если ключ провайдера отсутствует или является placeholder, интерфейс не имитирует результат, а показывает Beta/unavailable state.

Это позволяет независимо включать:

- hotels;
- flights;
- AI-анализ;
- hotel photos;
- partner booking.

## 5. Полный порядок работы сервиса

## 5.1. Регистрация и подготовка профиля

### Действие пользователя

Пользователь открывает страницу регистрации, вводит имя, email и пароль, принимает Terms и Privacy Policy, а также отдельно решает, разрешить ли поведенческое отслеживание.

### Что делает система

1. Клиент получает актуальные версии юридических документов.
2. Сервер валидирует формат данных и силу пароля.
3. Пароль хешируется и не хранится в открытом виде.
4. Создаётся пользователь.
5. Создаётся строка пользовательских предпочтений.
6. Сохраняются версии Terms и Privacy, принятые пользователем.
7. Сохраняется отдельное согласие или отказ от behavioural tracking.
8. Создаётся одноразовый verification token; в базе хранится его hash.
9. SMTP отправляет ссылку подтверждения email.
10. После подтверждения пользователь получает доступ к onboarding.

### Безопасность

- access JWT хранится в `HttpOnly` cookie;
- access token короткоживущий, по умолчанию 15 минут;
- refresh token ротируется при каждом обновлении;
- в PostgreSQL хранится только SHA-256 hash refresh token;
- изменяющие состояние cookie-запросы защищены CSRF-токеном;
- число попыток входа ограничено rate limiter;
- пользователь может видеть и отзывать другие активные сессии.

## 5.2. Onboarding и Preferences

### Действие пользователя

Пользователь задаёт:

- желательную звёздность;
- тип номера;
- вид из номера;
- желательные удобства;
- обязательные удобства;
- тип перелёта и максимальное число пересадок;
- класс и место в самолёте;
- предпочитаемые авиакомпании;
- стиль поездки;
- бюджетный уровень и лимит цены за ночь;
- чувствительность к шуму;
- любимые направления;
- настройки уведомлений.

### Что делает система

1. Сервер валидирует значения.
2. Настройки сохраняются в `user_preferences`.
3. Для завершения onboarding обязательно выбрать звёздность, удобства и бюджет.
4. Обязательные удобства далее становятся строгими SQL-фильтрами.
5. Желательные удобства участвуют в персональном Score.
6. При наличии согласия сохраняется событие `preference_changed`.
7. Объявленные веса становятся исходной точкой обучения.

## 5.3. Главная страница и выбор сценария

### Действие пользователя

Пользователь выбирает `Hotel`, `Flight` или `Package · Beta`, вводит пункт отправления, направление, даты, число гостей, цель поездки и при необходимости класс перелёта.

### Что делает система

1. Форма проверяет обязательные поля.
2. Город должен входить в поддерживаемый справочник.
3. Дата выезда должна быть позже даты заезда.
4. Данные поездки временно сохраняются в `sessionStorage`.
5. Клиент проверяет capability выбранного продукта.
6. Для Hotel выполняется переход на `/results`.
7. Для Flight выполняется переход на `/flights`.
8. Package остаётся Beta и не запускает фиктивный поиск.

На главной также показываются популярные направления. Они формируются из базы Tripalora и отображают минимальную доступную цену по городу, если такая цена существует.

## 6. Пользовательский путь поиска отеля

## 6.1. Шаг 1: первичный поиск по каталогу

### Действие пользователя

Пользователь запускает поиск по городу, датам, гостям и цели поездки.

### Участвующие компоненты

- React `ResultsPage`;
- `GET /api/hotels/search`;
- PostgreSQL;
- LiteAPI catalog sync;
- Hotel Index;
- таблицы пользовательских предпочтений и контекстных весов.

### Порядок обработки

1. API требует авторизацию, подтверждённый email и завершённый onboarding.
2. Проверяются будущие даты и корректность диапазона.
3. Сервер получает профиль пользователя.
4. Обязательные удобства объединяются с фильтрами текущего поиска.
5. Если каталог города отсутствует, Tripalora синхронно импортирует его через LiteAPI.
6. Если каталог уже есть, поиск не блокируется: его обновление запускается в фоне.
7. Из PostgreSQL выбираются активные отели нужного города.
8. Применяются строгие фильтры: звёзды, район, rating, обязательные amenities, free cancellation, breakfast и диапазон цены.
9. Отели, скрытые пользователем в том же контексте поездки, исключаются.
10. Загружаются номера, отзывы и подходящие сохранённые тарифы.
11. Строится сопоставимый рыночный benchmark.
12. Для всех кандидатов рассчитывается Hotel Index.
13. Вся выборка сортируется до пагинации.
14. Пользователю возвращается первая страница до 30 вариантов.

Поиск работает cache-first, чтобы внешний провайдер не удерживал весь экран десятки секунд.

## 6.2. Шаг 2: progressive live rates

После первичного ответа клиент отправляет видимые `hotel_ids` в `POST /api/hotels/rates/batch`.

Сервер:

1. проверяет до 50 отелей за один batch;
2. запрашивает LiteAPI rates для выбранных дат и гостей;
3. параллельно пытается получить цены Xotelo;
4. сохраняет тарифы, валюту, налоги, питание, отмену, номер и provider metadata;
5. отбрасывает невалидные и подозрительные цены;
6. заново строит comparable benchmark;
7. пересчитывает Score, Score Reliability и Price Confidence;
8. возвращает только отели с доступным сопоставимым тарифом как полноценные предложения;
9. сообщает IDs отелей, для которых тариф не найден;
10. клиент пересортировывает страницу.

Отель без подтверждённой цены:

- не должен выглядеть полноценным bookable offer;
- не получает `AI Top Pick`;
- может быть скрыт или показан отдельно как «Цена уточняется»;
- не конкурирует на равных с доступными вариантами.

## 6.3. Шаг 3: отображение результатов

Пользователь видит:

- название, район, звёздность и рейтинг;
- фотографию;
- важные amenities;
- Fairworth Score;
- Score Reliability;
- цену за ночь и сумму проживания;
- источник и свежесть цены;
- предупреждение о налогах или иных неизвестных условиях;
- признаки Top Pick и live/cached rate.

Доступны:

- сортировка по скорректированному Score, цене и рейтингу;
- строгие фильтры;
- list/map mode;
- добавление в сравнение;
- добавление в trip basket;
- скрытие отеля с указанием причины;
- переход в детали.

## 6.4. Шаг 4: карта результатов

Карта строится по координатам отелей. Маркеры связаны с карточками. Корзина открывается поверх карты благодаря отдельному overlay/z-index слою, поэтому карта не перекрывает управление поездкой.

## 6.5. Шаг 5: скрытие отеля

Пользователь выбирает причину:

- слишком дорого;
- не подходит район;
- не понравились фотографии;
- нет бассейна;
- низкая звёздность;
- другая причина.

Система:

1. записывает `hide` с сигналом `-4`;
2. сохраняет причину и контекст;
3. скрывает этот отель для аналогичного сценария поездки;
4. изменяет только связанный фактор обучения;
5. не делает необоснованных выводов из причины `photos` или `other`.

## 7. Подробная страница отеля

### Действие пользователя

Пользователь открывает `View details`.

### Какие сервисы работают

- `GET /api/hotels/:id`;
- PostgreSQL catalog, rooms, reviews, prices;
- Google Places Photos;
- Hotel Index;
- optional OpenRouter AI;
- interactions API;
- bookmarks и price watches.

### Порядок работы

1. Сервер загружает карточку, номера, отзывы и цены.
2. Google Places пытается сопоставить отель по имени, адресу и координатам.
3. При уверенном match загружается до настроенного числа фотографий.
4. Если Google Photos ничего не дал, остаются сохранённые 1-2 изображения.
5. Записывается первое событие `view` с нулевым обучающим сигналом.
6. Повторное открытие в другой сессии становится `revisit` с сигналом `+1.5`.
7. Просмотр галереи даёт `gallery_view +0.75`.
8. Открытие номеров даёт `rooms_open +1.25`.
9. При уходе со страницы может быть записан `dwell_time`.

### Why this Score

Блок объяснения показывает:

- версию формулы;
- время расчёта;
- базовый и adjusted score;
- Score Reliability;
- Price Confidence;
- веса компонентов;
- value, quality, trust и personal fit;
- рыночный benchmark;
- параметры тарифа;
- свежесть и структуру отзывов;
- совпадение типа номера и вида;
- найденные и ненайденные предпочтения;
- список неизвестных provider fields.

### AI analysis

По запросу пользователя Tripalora передаёт OpenRouter:

- описание отеля;
- amenities;
- комнаты;
- отзывы;
- цены и условия;
- даты;
- профиль пользователя.

AI возвращает структурированный JSON:

- персональный verdict;
- рекомендуемый номер;
- timing бронирования;
- предупреждения;
- совпадения и несовпадения;
- предпочтительного оператора.

AI-анализ сохраняется в `ai_analyses`. Он дополняет, но не заменяет детерминированный Hotel Index.

## 8. Сравнение отелей

Пользователь может добавить до трёх вариантов.

Система:

1. сохраняет добавление как `compare_add +2`, если tracking разрешён;
2. загружает единый набор параметров для каждого отеля;
3. показывает цены, Score, рейтинг, amenities и различия;
4. сохраняет `compare_session`;
5. при доступном OpenRouter получает AI verdict и winner;
6. при недоступном AI сохраняет возможность ручного сравнения.

Удаление из сравнения даёт более слабый отрицательный сигнал `compare_remove -1`.

## 9. Пользовательский путь поиска авиаперелёта

## 9.1. Запуск поиска

Пользователь задаёт маршрут, дату, пассажиров и cabin class.

Участвуют:

- React `FlightsPage`;
- `/api/flights/*`;
- Travelpayouts Data API;
- справочники аэропортов и авиакомпаний;
- Flight Index;
- пользовательские flight preferences.

## 9.2. Получение предложений

Tripalora может обращаться к нескольким endpoint Travelpayouts:

- cheap/top fares;
- direct fares;
- calendar;
- popular routes;
- static airport, city, country и airline data.

Ответ нормализуется. Каждому предложению добавляются:

- `fare_type = indicative`;
- момент наблюдения и получения цены;
- статус provider/local cache;
- `availability_confirmed = false`;
- `seat_availability_confirmed = false`;
- требование финальной проверки у поставщика.

Локальный кеш обычно хранится до трёх часов. Статические справочники кешируются примерно на сутки.

## 9.3. Расчёт индекса и сортировка

1. Выбирается cohort точной даты.
2. Если возможно, cohort сужается до requested cabin.
3. Считается медианная цена по одинаковому числу пересадок.
4. Находится минимальная достоверная длительность маршрута.
5. Для каждого варианта считаются Base Score, Reliability и Fare Confidence.
6. Применяются строгие ошибки cabin/max stops.
7. Сначала ранжируются Top Pick eligible варианты.
8. Затем используется adjusted score, base score и цена.

## 9.4. Что видит пользователь

- авиакомпанию и номер рейса;
- аэропорты;
- время вылета;
- длительность;
- число пересадок;
- цену за одного пассажира;
- полную стоимость для выбранного состава;
- Fairworth Flight Score;
- Score Reliability;
- Fare Confidence;
- время получения цены;
- предупреждение о том, что цена и место требуют проверки.

Если Travelpayouts не передал багаж, налоги, refundability, cabin или seat layout, Tripalora не придумывает эти данные.

## 11. Achievements

### Действие пользователя

Пользователь вводит страну или город, выбирает вариант и отмечает его как посещённый.

### Что происходит

1. Клиент ищет по локальному справочнику более чем из 10 тысяч городов.
2. Для города известны страна, регион, координаты и population.
3. `POST /api/achievements/visits` сохраняет запись только для текущего пользователя.
4. Страна закрашивается на карте.
5. Для города добавляется marker.
6. Счётчики стран и городов пересчитываются.
7. Дубликат того же места отклоняется.
8. Пользователь может удалить отметку.

Карта использует Mercator projection, масштабируется внутри своей области и не прокручивает страницу при zoom.

### Продуктовая ценность

Achievements создаёт эмоциональный retention loop: пользователь возвращается не только перед покупкой, но и для ведения собственной истории путешествий. В будущем посещённые страны могут использоваться как сигнал familiarity, но сейчас они не должны автоматически менять Score без отдельного согласия и продуктовой проверки.

## 12. Уведомления и сохранённые поездки

## 12.1. Price watch

Пользователь сохраняет отель, даты, гостей, валюту и target price.

Система хранит:

- baseline price;
- last price;
- lowest price;
- last notified price;
- время предыдущей и следующей проверки;
- параметры drop/rise alerts.

Частота проверки:

- более чем за 60 дней: примерно раз в 24 часа;
- за 15-60 дней: примерно раз в 12 часов;
- ближе 14 дней: примерно раз в 6 часов.

## 12.2. Trip reminders

Сохранённая поездка имеет destination, даты, status и набор trip items. Worker планирует напоминания за 7 дней, 24 часа и 3 часа.

## 12.3. Weekly digest

Weekly digest учитывает локаль, timezone, weekday и hour пользователя. В письмо могут попасть лучшие наблюдавшиеся цены за неделю.

## 12.4. Надёжность доставки

- задачи хранятся в PostgreSQL;
- есть deduplication key;
- worker использует row locking;
- выполняется до пяти попыток;
- stuck jobs восстанавливаются;
- доступна one-click unsubscribe;
- статусы `pending`, `processing`, `sent`, `failed`, `cancelled` можно анализировать.

## 13. Hotel Index: подробное описание

Текущая версия формулы: **4.5.0**.

## 13.1. Три результата расчёта

### Fairworth Hotel Score

Показывает персональную привлекательность отеля по шкале 0-100.

### Score Reliability

Показывает, насколько полно данные подтверждают Score.

### Price Confidence

Показывает, насколько надёжна конкретная цена для выбранных дат и гостей.

## 13.2. Базовая формула

| Компонент | Вес |
|---|---:|
| Personal preference match | 35% |
| Value | 25% |
| Hotel quality | 25% |
| Review confidence | 15% |

```text
Hotel Score =
    Personal Fit * 0.35
  + Value * 0.25
  + Quality * 0.25
  + Review Confidence * 0.15
```

Если компонент неизвестен, он исключается, а оставшиеся веса нормализуются. Неизвестность не равна нулю.

## 13.3. Value

Для budget и mid-range:

| Сигнал | Вес внутри Value |
|---|---:|
| Позиция относительно comparable market | 60% |
| Provider value-for-money rating | 40% |

Для upscale и luxury ценовая дешевизна исключается из Value, чтобы дешёвый отель не становился лучшим только из-за цены. В этих сценариях Value в большей степени опирается на оценку ценности гостями.

## 13.4. Comparable market price

Сегмент ищется по иерархии:

1. город + звёзды + район + категория номера;
2. город + звёзды + район;
3. город + звёзды + категория номера;
4. город + звёзды;
5. город.

Требуется минимум три предложения. Используются `P25`, median и `P75`, а не минимум текущей страницы.

Тариф нормализуется с учётом:

- полной стоимости проживания;
- числа ночей;
- состава гостей;
- налогов и обязательных сборов;
- категории номера;
- refundability;
- breakfast inclusion.

Сравнительная цена корректируется, если occupancy не подтверждён, налоги неизвестны, room type отличается, тариф невозвратный или отсутствует желаемый завтрак.

## 13.5. Quality

Базовый default profile:

| Сигнал | Вес |
|---|---:|
| Overall rating | 22.5% |
| Cleanliness | 22.5% |
| Service | 22.5% |
| Location | 22.5% |
| Review freshness | 10% |

Профиль меняется по стилю:

- **luxury:** service, cleanliness и premium facilities важнее;
- **business:** location, service, quiet, Wi-Fi и soundproofing;
- **family:** cleanliness, location и family facilities;
- **resort:** pool, beach, SPA, territory и food;
- **active:** gym, tennis и outdoor facilities;
- **gastronomy:** restaurant и breakfast.

Если стилей несколько, веса профилей усредняются.

## 13.6. Review freshness

Свежесть составляет 10% Quality.

| Сигнал | Вес внутри Freshness |
|---|---:|
| Latest review date | 40% |
| Share of reviews за 12 месяцев | 25% |
| Rating trend | 25% |
| Renovation freshness | 10% |

Система различает стабильность, улучшение, резкое улучшение, снижение и резкое снижение. Нехватка данных уменьшает reliability, а не intrinsic quality.

## 13.7. Review Confidence

| Сигнал | Вес |
|---|---:|
| Review volume | 40% |
| Freshness | 25% |
| Cross-source consistency | 20% |
| Verified stays | 10% |
| Integrity и dispersion | 5% |

Review volume использует логарифмическую шкалу. Также учитываются:

- число источников;
- разброс рейтингов;
- suspicious review share;
- verified review share;
- согласованность provider ratings.

Отдельно возвращается `review_confidence_reliability`.

## 13.8. Personal Fit

Исходные веса:

| Предпочтение | Вес |
|---|---:|
| Travel tier | 22% |
| Preferred amenities | 20% |
| Stars | 16% |
| Budget | 14% |
| Room type | 12% |
| Room view | 8% |
| Noise sensitivity | 8% |

Эти веса постепенно смешиваются с обученными глобальными и контекстными весами.

## 13.9. Amenities

- required amenities работают как строгие фильтры;
- preferred amenities влияют на Score;
- считается доля подтверждённых желательных amenities;
- разные amenities могут иметь разную важность;
- совпадение одного пункта не даёт всему блоку 100;
- если каталог amenities отсутствует целиком, результат unknown;
- если каталог есть, но amenity отсутствует, это известное несовпадение.

## 13.10. Travel tier и luxury

Для `mid`, `upscale`, `luxury` используются:

| Сигнал | Базовый вес |
|---|---:|
| Star fit | 15% |
| Verified quality | 13% |
| Service | 14% |
| Room condition | 10% |
| Room size | 9% |
| Premium amenities | 8% |
| Brand reputation | 7% |
| Breakfast quality | 7% |
| Room category | 6% |
| Luxury review semantics | 7% |
| Renovation freshness | 4% |

Если пользователь отдельно выбрал звёздность, вес stars внутри travel tier уменьшается с 15% до 5%. Это предотвращает двойной бонус за одну характеристику.

Luxury поэтому не определяется только пятью звёздами. Высокую оценку может получить сильный 4-star boutique hotel, а устаревший 5-star hotel со слабым сервисом не получает автоматическое преимущество.

## 13.11. Room type и view similarity

Иерархия категорий:

```text
standard -> superior -> deluxe -> executive -> junior suite -> suite -> villa
```

Примеры:

| Запрос | Реальный номер | Match |
|---|---|---:|
| suite | junior suite | 80 |
| junior suite | suite | 95 |
| deluxe | deluxe king room | 100 |
| king | deluxe king room | 100 |
| sea view | partial sea view | 75 |
| sea view | oceanfront | 100 |
| city view | skyline view | 100 |

## 13.12. Score Reliability

Reliability отражает:

- размер market sample;
- уверенность в taxes и occupancy;
- свежесть тарифа;
- полноту quality fields;
- полноту review confidence;
- наличие данных по пользовательским предпочтениям.

## 13.13. Price Confidence

Исходная уверенность выше для LiteAPI/Xotelo и уменьшается при:

- возрасте цены более 1, 6 и 12 часов;
- неизвестных налогах;
- неподтверждённом occupancy;
- room mismatch;
- stale status;
- demonstration/non-displayable status.

Stale price ограничивается 35. Demonstration или non-displayable price получает 0.

## 13.14. Adjusted Score

```text
Adjusted Hotel Score =
    Base Hotel Score * 0.80
  + Score Reliability * 0.10
  + Price Confidence * 0.10
```

Именно adjusted score используется при сортировке. Пользовательский base score остаётся объяснимой оценкой соответствия.

## 13.15. AI Top Pick

Минимальные условия:

- Price Confidence не ниже 60;
- цена не stale;
- цена не demonstration;
- price displayable;
- вариант доступен для выбранных дат и гостей.

## 13.16. Контекстное обучение

Контексты:

- leisure, business, family, couple;
- short, medium, long trip;
- destination;
- season;
- solo, pair, small group, large group.

Сигналы:

| Событие | Сила |
|---|---:|
| impression | 0 |
| первый view | 0 |
| dwell 20-59 sec | +0.5 |
| dwell 60-179 sec | +1 |
| dwell 180+ sec | +2 |
| gallery view | +0.75 |
| rooms open | +1.25 |
| revisit | +1.5 |
| compare add | +2 |
| trip add | +3 |
| bookmark add | +3 |
| provider click | +4 |
| booking intent | +5 |
| checkout started | +6 |
| booking completed | +10 |
| compare remove | -1 |
| bookmark remove | -2 |
| trip remove | -2.5 |
| hide | -4 |

Обучение работает только при consent. Простой просмотр не считается позитивным намерением.

## 14. Flight Index: подробное описание

Текущая версия: **1.0.0**.

## 14.1. Базовая формула

Default weights:

| Компонент | Вес |
|---|---:|
| Value | 30% |
| Itinerary | 30% |
| Preferences | 25% |
| Schedule | 15% |

Если поле неизвестно, его вес исключается из применимого среднего.

## 14.2. Context weights

| Контекст | Value | Itinerary | Preferences | Schedule |
|---|---:|---:|---:|---:|
| Default | 30 | 30 | 25 | 15 |
| Budget | 42 | 25 | 20 | 13 |
| Business | 20 | 35 | 25 | 20 |
| Family | 25 | 35 | 25 | 15 |
| Short trip до 3 дней | 22 | 38 | 25 | 15 |

## 14.3. Value

Цена сравнивается с медианой:

- точной даты;
- по возможности того же cabin;
- того же числа пересадок.

Пусть `ratio = price / benchmark`.

- ratio до 0.70: 100;
- от 0.70 до 1.00: плавно 100 -> 82;
- от 1.00 до 1.50: плавно 82 -> 45;
- выше 1.50: дальнейшее снижение, но обычно не ниже 20.

Также возвращаются unit price, passenger count и total for party.

## 14.4. Itinerary

```text
Itinerary = Duration Score * 55% + Stops Score * 45%
```

Duration сравнивается с самым быстрым credible itinerary cohort. Чем больше отношение к baseline, тем ниже оценка; нижняя граница около 30.

Stops:

- direct получает 100;
- family/business сильнее штрафуют пересадки;
- leisure допускает их немного мягче;
- 3+ stops получает минимальную применимую оценку.

Layover duration, airport changes и overnight connections предусмотрены моделью данных, но остаются unknown, пока провайдер не отдаёт segments.

## 14.5. Schedule

- вылет с 07:00 до 20:00: 100;
- с 05:00 до 23:00: 82, а для business 72;
- ночное время: 62, а для business 48.

## 14.6. Preference Fit

| Сигнал | Вес внутри Preferences |
|---|---:|
| Preferred airline | 35% |
| Cabin class | 35% |
| Max stops | 20% |
| Group seating | 10% |

Cabin mismatch и превышение подтверждённого max stops являются strict failures. Unknown cabin не считается mismatch.

## 14.7. Пассажиры и рассадка

Если пассажир один, seating score равен 100.

Для группы система читает:

- `seat_blocks`;
- `seat_layout`, например `2-4-2`;
- `seats_abreast`.

Логика:

- точный боковой блок на размер группы: 100;
- для пары блок на 3 места: примерно 72;
- больший блок для другой группы: около 80;
- если группу придётся делить на несколько рядов, оценка снижается;
- если layout неизвестен, результат unknown и base score не штрафуется.

Travelpayouts обычно не предоставляет надёжную seat map, поэтому Tripalora не угадывает компоновку по airline или flight number.

## 14.8. Fare Confidence

Начальная оценка Travelpayouts Data API — 62, поскольку это индикативный cached observation.

Она снижается при:

- price calendar source;
- local cache;
- alternative date;
- отсутствии booking link;
- отсутствии fare expiry;
- неизвестных или исключённых taxes;
- неизвестном baggage;
- неизвестной refundability;
- неподтверждённом cabin;
- неподтверждённой party price;
- неизвестном или старом `fare_observed_at`.

Всегда считаются неизвестными подтверждённая availability и seat inventory, пока не подключён booking/search API соответствующего уровня.

## 14.9. Score Reliability

Reliability строится из покрытия core fields:

- price;
- stops;
- duration;
- departure schedule;
- cabin;
- seat layout для группы.

Также учитывается размер benchmark sample, максимум с ограниченным бонусом.

## 14.10. Adjusted Flight Score

```text
Adjusted Flight Score =
    Base Flight Score * 0.80
  + Score Reliability * 0.10
  + Fare Confidence * 0.10
```

## 14.11. Top Pick

Fare eligible, если:

- нет strict filter failures;
- Reliability не ниже 55;
- Fare Confidence не ниже 45;
- дата не alternative;
- предложение относится к нужному поисковому контексту.

## 14.12. Главная честность Flight Index

Flight Score оценивает удобство и соответствие, но не утверждает наличие конкретного места. Интерфейс обязан сообщать, что финальная цена, налоги, багаж и seat availability проверяются у поставщика.

## 17. Как использовать аналитику для развития продукта

### Приоритизация провайдеров

Если в городе высокий спрос, но низкий live-rate coverage, это прямой аргумент подключить дополнительного hotel API. Если Flight Fare Confidence системно низок из-за baggage/taxes/cabin, нужен richer search/booking API, а не ещё одна корректировка формулы.

### Калибровка индексов

Вес следует менять не по субъективному впечатлению, а по связи компонентов с:

- compare add;
- trip add;
- checkout started;
- booking completed;
- hide reason.

Изменения формулы нужно выпускать под новой version и сравнивать на одинаковых cohorts.

### Улучшение UX

- высокий detail view, но низкий trip add: проблема карточки, цены или доверия;
- высокий trip add, но низкий checkout: проблема корзины или состава тура;
- высокий checkout start, но низкий completion: проблема формы или требований к данным;
- много `photos` feedback: недостаточная или нерелевантная галерея;
- много `too_expensive`: неверная аудитория, бюджетные настройки или price coverage;
- много `bad_location`: нужны более сильные district filters и карта.

### Персонализация

Контекстные веса позволяют не смешивать luxury leisure и budget business. Но любые новые персональные сигналы следует вводить постепенно, с минимальным evidence threshold и возможностью объяснить результат.

### Retention

Price watches, trips, reminders и Achievements создают причины вернуться между покупками. Аналитика должна показать, какой из этих loops действительно приводит к повторному поиску и оформлению.

## 18. Privacy и ограничения аналитики

- behavioural events записываются только после optional consent;
- пользователь может изменить consent;
- пользователь может экспортировать данные;
- пользователь может удалить аккаунт;
- user-owned записи удаляются каскадно;
- raw activity имеет ограниченный срок хранения;
- полные платёжные реквизиты не собираются;
- реальной оплаты в MVP нет;
- аналитика должна использовать агрегаты и минимально необходимую детализацию;
- подключение рекламных, email-open или cross-device трекеров требует отдельной legal/privacy оценки.

По умолчанию activity history, searches, interactions, comparisons, AI analyses и score snapshots очищаются по retention policy, обычно около 24 месяцев. Технические и кеш-данные имеют более короткий срок.

## 19. Сильные стороны текущего MVP

1. Tripalora не подменяет отсутствующие provider data фиктивными предложениями.
2. Отдельно моделируются полезность, надёжность Score и надёжность цены.
3. Missing data не считается плохим качеством.
4. Отельные цены сравниваются в релевантном market segment.
5. Luxury шире звёздности.
6. Качество зависит от travel style.
7. Отзывы учитывают свежесть, структуру и согласованность.
8. Amenities поддерживают строгие и желательные требования.
9. Room/view matching допускает частичное совпадение.
10. Обучение опирается на meaningful actions, а не на простой click.
11. Контексты поездок разделены.
12. Негативный feedback объясняет причину.
13. Flight Index честно обозначает индикативный характер fares.
14. Демо-checkout позволяет проверить намерение без ложного обещания брони.
15. Уже существует достаточно данных для построения продуктовой воронки и калибровки индексов.

## 20. Ограничения и следующие шаги после закрытого MVP

### Продукт

- провести полный rebranding внутренних и юридических упоминаний Fairworth -> Tripalora;
- собрать feedback первых пользователей;
- определить главный North Star Metric;
- подтвердить, нужен ли packages flow в следующей версии;
- решить, какие уведомления реально повышают retention.

### Hotel supply

- измерить live-rate coverage по каждому городу;
- подключать дополнительного провайдера только там, где подтверждён gap;
- улучшать room mapping;
- повышать tax/occupancy/meal/cancellation completeness.

### Flight supply

- перейти от cached indicative fares к полноценному flight search API;
- получать сегменты, layovers, baggage, refundability и cabin confirmation;
- подключить seat-map provider, если group seating доказал ценность.

### Индексы

- не усложнять формулы до накопления реальных outcome data;
- добавить reliability threshold для Hotel Top Pick;
- калибровать веса по действиям compare, trip add и checkout;
- проводить versioned offline evaluation;
- отслеживать fairness между городами и провайдерами.

### Аналитика

- построить dashboard funnel и provider coverage;
- разделить operational, product и model metrics;
- добавить event taxonomy documentation;
- определить владельца качества данных;
- отслеживать consent rate и не смешивать consented/non-consented cohorts.

### Booking и monetization

- зарегистрировать партнёрские аккаунты;
- включить partner flow только после проверки allowed hosts, deep links и signed postbacks;
- провести staging end-to-end с реальным provider return;
- не считать demo bookings реальной выручкой.

## 22. Итог

Tripalora в текущем состоянии — не просто интерфейс поиска. Это персонализированная система принятия решения, где предложение оценивается одновременно по качеству, цене, контексту пользователя и надёжности данных.

Главная ценность MVP состоит в четырёх вещах:

1. **Честная выдача:** отсутствие данных не маскируется и не превращается в фиктивную уверенность.
2. **Персонализация:** один и тот же вариант может быть по-разному полезен в разных сценариях поездки.
3. **Объяснимость:** пользователь может понять, почему получил конкретный Score.
4. **Готовность к обучению на MVP:** система уже собирает действия, цены, контексты и результаты, необходимые для последующей калибровки.

Следующий этап развития — не бесконечно усложнять эвристики, а проверить их на поведении закрытой аудитории, измерить provider coverage и конверсию, после чего принимать решения на основании накопленных данных.
